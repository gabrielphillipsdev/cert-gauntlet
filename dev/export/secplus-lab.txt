[dg-screened] sim=diagram domain=3 obj=3.2 (Given a scenario, apply security principles to secure enterprise infrastructure)
TITLE: Build the screened subnet
PROMPT: Place each security device where it belongs on the topology. Not every palette item is used.
TASK:
    1. Put the device that separates the Internet from every internal zone at slot A.
    2. Protect web01 against HTTP-layer attacks (SQLi, XSS) with the device that understands HTTP, at slot B.
    3. Administrators must reach DMZ servers only by first logging in to a hardened host inside the DMZ (slot C).
    4. Slot D receives a mirrored copy of core-switch traffic and must never be able to drop a packet.
TOPOLOGY NODES: inet="Internet" (cloud), core="Core switch" (sw), dmz="DMZ" (zone), web="web01" (srv), lan="Internal LAN" (zone), users="Users" (pc), fs="File server" (srv)
LINKS: inet—A, A—core, core—B, B—web, core—C, core—users, core—D
PALETTE: firewall=Firewall, waf=Web application firewall, jump=Jump box, ids=IDS (passive), ips=IPS (inline), proxy=Forward proxy, lb=Load balancer, vpn=VPN concentrator
SLOTS (key):
    A · Edge  →  firewall | ngfw   // The boundary device is a firewall; the screened subnet is the zone it creates between its external and internal interfaces.
    B · Before web01  →  waf   // Only a web application firewall parses HTTP and blocks injection and scripting payloads; a network firewall sees ports, not SQL.
    C · Admin hop  →  jump | bastion   // A jump box (bastion) in the DMZ is the single hardened entry point for administration; admins never connect straight to the servers.
    D · SPAN copy  →  ids   // A device fed from a SPAN/mirror port is out of band: it can only detect and alert. That is an IDS; an IPS must be inline to block.
TAKEAWAY: Firewall at the boundary, WAF in front of the web tier, jump box for administration, IDS on a mirror port (passive) vs IPS inline (active). The slot's position tells you active-vs-passive before you even read the label.

[dg-inline] sim=diagram domain=3 obj=3.2 (Given a scenario, apply security principles to secure enterprise infrastructure)
TITLE: Inline or out of band?
PROMPT: Place the monitoring and detection devices. The link each slot sits on tells you whether it can block.
TASK:
    1. Slot A sits directly on the path between the firewall and the core switch and must stop known attacks in real time.
    2. Slot B hangs off the core switch's mirror (SPAN) port and must analyze every packet without ever becoming a point of failure.
    3. Slot C receives syslog and event feeds from the firewall, the core switch and the servers for correlation and alerting.
    4. Slot D is a deliberately exposed decoy host on the server VLAN that should generate an alert on any connection.
TOPOLOGY NODES: inet="Internet" (cloud), fw="Firewall" (box), core="Core switch" (sw), users="Users" (pc), srv="Server VLAN" (srv)
LINKS: inet—fw, fw—A, A—core, core—users, core—srv, core—B, fw—C, core—C, srv—D
PALETTE: ips=IPS (inline), ids=IDS (passive), siem=SIEM collector, honeypot=Honeypot, tap=Network tap, waf=Web application firewall, proxy=Forward proxy, lb=Load balancer
SLOTS (key):
    A · inline  →  ips   // Inline on the traffic path = can drop packets = IPS. An IDS placed here would still only alert.
    B · SPAN feed  →  ids   // Fed by a mirror port, the device sees a copy; it can detect and alert but cannot block. That is an IDS (passive).
    C · log feeds  →  siem   // A SIEM aggregates and correlates logs from every source; it is not on the traffic path at all.
    D · decoy  →  honeypot   // A honeypot is an intentionally vulnerable host with no legitimate users, so any touch is a high-fidelity alert.
TAKEAWAY: Inline (active) can block: IPS, firewall, WAF. Out of band (passive) only alerts: IDS, sensor, SIEM. A SPAN port or tap feeds the passive devices. Honeypots are deception, not detection, but they alert on any contact.

    A · tunnels end  →  vpn   // A VPN concentrator terminates IPsec/TLS tunnels; the firewall then polices the decrypted traffic.
    B · admin hop  →  jump | bastion   // A jump box (bastion host) is the hardened, logged chokepoint for administration; MFA and session recording live here.

[hd-web] sim=hardening domain=4 obj=4.1 (Given a scenario, apply common security techniques to computing resources)
TITLE: Harden a public web server
PROMPT: Reduce the attack surface without taking the site down.
TASK:
    1. The site must keep serving HTTPS, and HTTP must keep redirecting to it.
    2. Remove every service and open port that the stated role does not need.
    3. MySQL is used only by the local application; it must never be reachable from the network.
    4. Admins connect over SSH from the VPN only; root must not be able to log in over SSH.
    5. Patches must install automatically; the host firewall must be on with a default-deny inbound policy.
HOST: web01 · Ubuntu Server 22.04 · Public HTTPS site; the app reads a local MySQL database; admins SSH in over the VPN
CONTROLS ('*' = scored; 'crit' = changing it breaks the business function, −1; unmarked = leave alone, −½ if changed):
  Services
    ! nginx (web server): start=Running  [crit: keep]   // The business function is the website.
    ! mysqld (database): start=Running  [crit: keep]   // The application reads the local database; stopping it breaks the site. Restrict it instead.
    * telnetd: start=Running  →  KEY=Stopped   // Cleartext remote login; SSH replaces it entirely.
    * vsftpd (FTP): start=Running  →  KEY=Stopped   // Cleartext file transfer with no stated use; SFTP over SSH covers any real need.
    * cups (printing): start=Running  →  KEY=Stopped   // A web server does not print. Unused services are unpatched attack surface.
    ! sshd: start=Running  [crit: keep]   // Admins need SSH; the task is to restrict it, not remove it.
  Host firewall
    * Host firewall (ufw): start=Disabled  →  KEY=Enabled
    * Default inbound policy: start=Allow all  →  KEY=Deny all except allowed rules   // Implicit deny: open only what is listed.
  Listening ports (reachable from the network)
    ! TCP 80 (HTTP) (Redirects to HTTPS): start=Open  [crit: keep]   // The task says HTTP must keep redirecting.
    ! TCP 443 (HTTPS): start=Open  [crit: keep]
    * TCP 22 (SSH) — source: start=Any  →  KEY=VPN subnet 10.0.9.0/24 only   // Admins arrive via the VPN; nobody else needs SSH. Closing it entirely locks the admins out.
    * TCP 3306 (MySQL): start=Open  →  KEY=Closed   // The database is local-only; bind it to localhost and close the port.
    * TCP 21 (FTP): start=Open  →  KEY=Closed
    * TCP 23 (Telnet): start=Open  →  KEY=Closed
  Accounts & remote access
    * PermitRootLogin (SSH): start=Yes  →  KEY=No   // Admins log in as themselves and escalate with sudo; that keeps an audit trail and removes the one username every attacker already knows.
    * Account: guest (default, no password): start=Enabled  →  KEY=Disabled
    ! Account: webadmin (sudo): start=Enabled  [crit: keep]   // That is how the admins get in.
    * VNC remote desktop: start=On  →  KEY=Off   // Unneeded remote-access path; SSH is the sanctioned one.
  Updates
    * Unattended security updates: start=Off  →  KEY=On
      Full-disk encryption (LUKS): start=Off  [leave alone]   // Not in the requirement for this change; encrypting a running server's disk is a separate project.
TAKEAWAY: Hardening = remove what the role does not need (services, ports, accounts), restrict what it does need (SSH from the VPN, DB local-only), and turn on the baseline controls (host firewall default-deny, automatic patching). Breaking the business function is a failed change, not a hardened host.

        why wrong: The SLE and ALE values are reversed; the per-event loss is larger than the annualized figure when ARO is below 1.
TAKEAWAY: SLE = asset value x exposure factor = $250,000 x 0.40 = $100,000. ALE = SLE x ARO = $100,000 x 0.5 = $50,000.

[s-perm] sim=scenario domain=- obj=2.3 (Explain various types of vulnerabilities)
TITLE: Exhibit: Script and file permissions
SETUP: During an audit of a Linux backup server, an analyst finds the following script and its permissions.
EXHIBIT:
    $ ls -l /opt/backup/sync.sh
    -rwxrwxrwx 1 root root 412 Aug 30 02:10 /opt/backup/sync.sh
    
    $ cat /opt/backup/sync.sh
    #!/bin/bash
    DB_USER=backup_admin
    DB_PASS=Backup#2024!
    mysqldump -u $DB_USER -p$DB_PASS orders > /mnt/nas/orders.sql
    
    $ crontab -l
    0 2 * * * /opt/backup/sync.sh
Q: Which of the following BEST describes the MOST serious vulnerability?
  * A. Hard-coded credentials in a world-writable script that runs as root nightly
    B. The backup runs at 02:00 when no one is monitoring
        why wrong: The schedule is normal for backups; timing is not a security flaw.
    C. mysqldump output is not compressed
        why wrong: Compression is an efficiency choice and has no bearing on the exposure of credentials or root execution.
    D. The script uses bash instead of Python
        why wrong: The language is irrelevant; the same secrets and permissions problem would exist in any script.
TAKEAWAY: The database password is stored in plaintext, and mode 777 lets any local user read it or replace the script's contents. Because root's cron executes the file, an attacker can gain root by editing it. Fix by moving the secret to a protected credentials file or vault and setting permissions to 700.
