# SC-200 confusable twins
# Each statement is tagged with the side it is true of. Flag any statement that is true of the other side, or of both.

[1] A = Scheduled analytics rule   |   B = NRT analytics rule   (obj 1.4.3)
CONTRAST: A scheduled rule runs its KQL on an interval you choose, from every five minutes to every 14 days, over a lookback window of the same range, and runs about five minutes behind the clock to allow for ingestion. An NRT rule is a stripped-down scheduled rule that runs once a minute over the previous minute of ingested data, with a cap of 50 per workspace.
  (A) Run interval and lookback are configurable from 5 minutes to 14 days
  (A) Executes on a 5-minute delay to allow data to arrive
  (A) Supports up to 150 single-event alerts per execution
  (B) Runs once every minute with a one-minute lookback
  (B) Limited to 50 rules per workspace
  (B) Queries on ingestion time rather than TimeGenerated

[2] A = Hunting query   |   B = Analytics rule   (obj 3.2.1)
CONTRAST: A hunting query is saved KQL with tactic and entity metadata that runs only when an analyst runs it and leaves no trace except bookmarks. An analytics rule runs automatically on a schedule and converts results into alerts and incidents. The hunting page offers Create analytics rule to promote a proven query.
  (A) Executes only when an analyst runs it
  (A) Results are not stored unless bookmarked
  (A) Listed on the Hunting page with a Results delta column
  (B) Runs automatically on a schedule or in near real time
  (B) Generates alerts that can become incidents
  (B) Configured through the Analytics wizard

[3] A = Workbook   |   B = Notebook   (obj 3.2.4)
CONTRAST: A workbook is a no-code dashboard of KQL charts and grids rendered inside the Sentinel or Defender portal. A notebook is a Jupyter document with Python cells that runs on Azure Machine Learning compute (or Spark for the data lake) and can apply machine learning, external data and custom visualisations.
  (A) Built from parameterised KQL visualisations without code
  (A) Viewed and shared inside the portal; needs only workspace read
  (A) Templates ship with content hub solutions
  (B) Runs Python cells on Azure Machine Learning compute
  (B) Uses MSTICPy for enrichment and process-tree visuals
  (B) Suited to custom machine learning over security data

[4] A = Microsoft Defender for Endpoint   |   B = Microsoft Defender for Identity   (obj 2.1.6)
CONTRAST: Defender for Endpoint is the EDR sensor on workstations and servers, producing the Device* advanced hunting tables and device response actions. Defender for Identity is a sensor on domain controllers, AD FS, AD CS and Entra Connect servers that watches directory traffic, producing the Identity* tables and identity-focused alerts such as DCSync and Kerberoasting.
  (A) Sensor installed on workstations and servers
  (A) Populates DeviceProcessEvents and DeviceNetworkEvents
  (A) Provides isolate device and live response actions
  (B) Sensor installed on domain controllers and AD FS servers
  (B) Populates IdentityLogonEvents and IdentityDirectoryEvents
  (B) Raises reconnaissance and lateral-movement alerts based on AD traffic

[5] A = Microsoft Defender for Identity   |   B = Microsoft Defender for Cloud Apps   (obj 2.1.4)
CONTRAST: Defender for Identity monitors on-premises Active Directory through domain controller sensors. Defender for Cloud Apps is a cloud access security broker that discovers shadow IT, connects to SaaS apps through APIs and controls sessions through Conditional Access App Control, producing the CloudAppEvents table.
  (A) Monitors on-premises Active Directory traffic
  (A) Detects DCSync, pass-the-ticket and account enumeration
  (B) Discovers shadow IT from firewall and proxy logs
  (B) Applies session policies through Conditional Access App Control
  (B) Populates CloudAppEvents for connected SaaS apps
  (A) Requires sensors on domain controllers

[6] A = Microsoft Defender for Endpoint   |   B = Microsoft Defender for Cloud Apps   (obj 2.1.4)
CONTRAST: Defender for Endpoint protects devices with EDR, vulnerability management and attack surface reduction. Defender for Cloud Apps protects the use of cloud applications, including OAuth app governance, file governance and real-time session control; the two integrate so that endpoint network signals feed cloud discovery.
  (A) Enforces attack surface reduction rules on devices
  (A) Offers device isolation and investigation packages
  (A) Sends device network signals into cloud discovery
  (B) Governs OAuth app permissions and unsanctioned apps
  (B) Blocks downloads in a browser session via reverse proxy
  (B) Scans files at rest in connected SaaS apps

[7] A = Incident   |   B = Alert   (obj 2.1.7)
CONTRAST: An alert is a single detection raised by a product or an analytics rule about one piece of suspicious activity. An incident is the case object that groups related alerts and their entities, carries status, severity, owner and classification, and is what analysts assign and close.
  (B) Single detection from one product or rule
  (B) Many of them can be correlated into one case
  (B) Stored in SecurityAlert and AlertInfo
  (A) Has an owner, status and classification
  (A) Groups related alerts and entities into one case
  (A) Automation rules trigger on its creation or update

[8] A = Automation rule   |   B = Playbook   (obj 1.1.10)
CONTRAST: An automation rule is a Sentinel-native object that reacts to incident or alert triggers with conditions and ordered actions such as assigning, tagging, changing severity or running a playbook. A playbook is an Azure Logic App that performs the actual integration work, such as posting to Teams, enriching with TI or blocking an IP.
  (A) Defined inside Sentinel with conditions and ordered actions
  (A) Can change severity, status, owner and tags directly
  (A) Has an order number and optional expiration date
  (B) Is an Azure Logic App workflow
  (B) Can call external APIs such as Teams or a firewall
  (B) Needs a Microsoft Sentinel trigger (incident, alert or entity) to be run from Sentinel

[9] A = Sentinel hunting queries   |   B = Defender XDR advanced hunting   (obj 3.1.3)
CONTRAST: Sentinel hunting queries are catalogued, metadata-rich KQL saved on the Hunting page, run in bulk and tracked with results deltas, bookmarks and hunts. Advanced hunting is the interactive KQL editor in the Defender portal that queries native XDR tables with 30-day retention and, once a workspace is onboarded, Sentinel and data lake tables too.
  (A) Catalogued with MITRE tactics and a Run all queries button
  (A) Supports hunts with hypothesis state and bookmarks
  (A) Installed from content hub solutions
  (B) Interactive editor with Timestamp-based XDR tables
  (B) Native data limited to 30 days unless extended through Sentinel
  (B) Offers Take action on result rows and Go hunt from incidents

[10] A = Logic App trigger: Microsoft Sentinel incident   |   B = Logic App trigger: Microsoft Sentinel alert   (obj 1.1.11)
CONTRAST: The incident trigger fires on incident creation or update, passes the whole incident with its alerts and entities, and is the only one automation rules can invoke. The alert trigger fires on a single alert, is run manually or from the analytics rule's alert automation, and cannot be called by automation rules.
  (A) Can be attached to an automation rule
  (A) Passes incident properties plus arrays of alerts and entities
  (A) Recommended by Microsoft for most scenarios
  (B) Fires on one alert rather than a case
  (B) Cannot be invoked by automation rules
  (B) Not usable with alerts from Microsoft security analytics rules

[11] A = Logic App trigger: Microsoft Sentinel entity   |   B = Logic App trigger: Microsoft Sentinel incident   (obj 1.1.11)
CONTRAST: The entity trigger runs a playbook on demand against a single entity such as an account, host or IP from an entity page or the incident's entities list, and cannot be automated. The incident trigger runs on the whole incident and is what automation rules call.
  (A) Run manually against one account, host, IP or URL
  (A) Available from entity pages during investigation
  (A) Cannot be called by automation rules
  (B) Fires when an incident is created or updated
  (B) Receives alerts and entities as arrays
  (B) Used by automation rules to run playbooks

[12] A = Data collection rule (DCR)   |   B = Data connector   (obj 1.3.2)
CONTRAST: A data connector is the Sentinel content object that represents a data source, documents prerequisites and shows connection status. A data collection rule is the Azure Monitor object that tells the Azure Monitor Agent exactly which events to collect, with XPath filters, and which workspace table receives them.
  (A) Azure Monitor object associated with the Azure Monitor Agent
  (A) Uses XPath queries to filter Windows event IDs
  (A) Specifies the destination workspace
  (B) Content object listed in the Sentinel Data connectors page
  (B) Shows connection status and last data received
  (B) Installed from a content hub solution

[13] A = Windows Security Events via AMA   |   B = Windows Event Forwarding (WEF)   (obj 1.3.3)
CONTRAST: Windows Security Events via AMA installs the Azure Monitor Agent on each Windows machine and uses a DCR to collect Security log events straight into SecurityEvent. WEF has Windows machines forward events natively to a collector server, where a single agent picks them up; the connector that reads a WEF collector writes to WindowsEvent.
  (A) Agent on every source machine
  (A) Collection scope defined by a data collection rule
  (A) Writes into the SecurityEvent table
  (B) Machines forward to a Windows Event Collector with no agent of their own
  (B) Uses subscriptions configured by Group Policy
  (B) Collected events land in the WindowsEvent table

[14] A = Syslog via AMA   |   B = Common Event Format (CEF) via AMA   (obj 1.3.4)
CONTRAST: Both connectors use the Azure Monitor Agent on a Linux log forwarder with a DCR that selects facilities and severities. Syslog via AMA stores raw syslog messages in the Syslog table, while CEF via AMA parses CEF-formatted messages into the typed columns of CommonSecurityLog; using the same facility in both duplicates data.
  (A) Destination table is Syslog
  (A) Message text stays in SyslogMessage for parse or extract
  (A) Appropriate for Linux auth and daemon logs
  (B) Destination table is CommonSecurityLog
  (B) Fields such as DeviceVendor and DeviceAction are parsed automatically
  (B) Used for firewalls and proxies that emit CEF

[15] A = Analytics tier   |   B = Data lake tier   (obj 1.2.2)
CONTRAST: The analytics tier is the hot store used by analytics rules, hunting, workbooks and incidents, with interactive retention up to two years. The data lake tier is low-cost long-term storage, up to twelve years, reached through data lake exploration KQL, KQL jobs and notebooks rather than by analytics rules.
  (A) Queried by analytics rules and interactive hunting
  (A) Interactive retention configurable up to 2 years
  (A) Higher per-GB cost
  (B) Retention configurable up to 12 years
  (B) Queried through KQL jobs, lake KQL queries and notebooks
  (B) Not used by analytics rules for alerting

[16] A = Interactive (analytics) retention   |   B = Total (long-term) retention   (obj 1.2.2)
CONTRAST: Interactive retention is how long a table stays in the analytics tier for rules and hunting; Sentinel's default is 90 days and the maximum is two years. Total retention is the full life of the data including the mirrored copy in the data lake, up to twelve years, and is what you set for compliance.
  (A) Sentinel security tables get 90 days at no charge; workspace default is otherwise 30 days
  (A) Maximum of 2 years
  (A) Data available to analytics rules during this period
  (B) Can be set up to 12 years
  (B) Covers the data lake copy after the analytics period ends
  (B) Chosen for compliance and forensic lookback

[17] A = Custom detection rule (Defender XDR)   |   B = Analytics rule (Microsoft Sentinel)   (obj 1.4.1)
CONTRAST: A custom detection rule is written in advanced hunting, must return Timestamp and ReportId, runs at fixed frequencies (24h, 12h, 3h, 1h or continuous) and can take device, user, file and email actions automatically. An analytics rule is a Sentinel object with flexible scheduling, entity mapping, incident grouping and automation rules.
  (A) Query must return Timestamp and ReportId
  (A) Frequency choices are 24h, 12h, 3h, 1h or Continuous (NRT)
  (A) Can isolate a device or quarantine a file as a built-in response
  (B) Scheduling from 5 minutes to 14 days
  (B) Uses entity mapping and alert-to-incident grouping settings
  (B) Triggers Sentinel automation rules

[18] A = Threat intelligence analytics rule   |   B = Scheduled analytics rule   (obj 1.4.3)
CONTRAST: Threat intelligence rules are templates that match imported indicators against log sources such as CEF, syslog and DNS without you writing the matching logic. A scheduled rule runs any KQL you supply on your own interval and lookback.
  (A) Matches ThreatIntelIndicators against incoming logs automatically
  (A) Logic is provided by the template rather than authored
  (A) Depends on indicators imported through a TI connector
  (B) Runs arbitrary KQL you write

[19] A = Anomaly rule   |   B = Fusion (advanced multistage attack detection)   (obj 1.4.5)
CONTRAST: Anomaly rules are customizable machine-learning detections that score behaviours against a baseline and write results to the Anomalies table instead of raising alerts. Fusion is a single, non-customizable ML rule that correlates low-fidelity signals across products into high-fidelity multistage incidents.
  (A) Writes results to the Anomalies table rather than alerts
  (A) Threshold and parameters can be tuned per anomaly
  (A) Can be run in flighting mode before production
  (B) One rule instance per workspace, enabled by default
  (B) Correlates alerts from multiple products into one incident
  (B) Internal logic is hidden and cannot be edited

[20] A = Fusion   |   B = Scheduled correlation rule   (obj 1.4.3)
CONTRAST: Fusion correlates low-fidelity alerts and anomalies from many products into a multistage incident using Microsoft's ML, with nothing to author. A scheduled correlation rule is KQL you write that joins or sequences events yourself and then alerts on the combined result.
  (A) Machine learning correlation maintained by Microsoft
  (A) Combines alerts across products into a single high-severity incident
  (A) Enabled by default and not customizable
  (B) Correlation logic is written in KQL by the analyst
  (B) Can join SecurityAlert with raw tables on your own keys
  (B) Interval and lookback are set in the rule wizard

[21] A = Live response   |   B = Investigation package   (obj 2.2.2)

Collecting an investigation package is a one-shot action that gathers autoruns, prefetch, event logs, network state and more into a downloadable archive.
  (A) Interactive shell session with commands like getfile and run
  (A) Must be enabled under Advanced features first
  (A) Session times out after 30 minutes of inactivity
  (B) One-click action that produces a downloadable archive
  (B) Includes autoruns, prefetch files, scheduled tasks and the Security event log

Restrict app execution applies a code integrity policy so only Microsoft-signed executables can run, leaving the network untouched.

  (B) Applies a code integrity policy

AIR investigates individual alerts, determines verdicts for entities and remediates them according to the device group's automation level.
  (A) Triggered by incident-level correlation with very high confidence
  (A) Actions are containment such as contain user and contain device
  (A) Marks incidents with an Attack Disruption tag and banner

[41] A = join   |   B = union   (obj 3.1.2)
CONTRAST: join matches rows from two tables horizontally on a key, with flavors such as innerunique (the default), inner, leftouter and leftanti. union stacks rows from several tables vertically, regardless of schema, and can tag each row with its source table.

  (A) leftanti variant finds rows with no match

[42] A = has   |   B = contains   (obj 3.1.2)
CONTRAST: has matches a whole indexed term of three or more characters and is the faster, recommended operator. contains matches any substring, so it finds fragments inside longer words but scans more data. Both are case-insensitive; the _cs variants are case-sensitive.
  (A) Matches complete terms only
  (A) Uses the term index for speed
  (A) Would not find Explorer inside KustoExplorerQueryRun
  (B) Matches any substring
  (B) Slower on large tables
  (B) Would find Explorer inside KustoExplorerQueryRun

  (A) Statement that precedes the pipeline and ends with a semicolon
  (A) Can hold a dynamic list for use with in or has_any
  (A) Can wrap a sub-query in materialize()
  (B) Pipeline operator that appends columns
  (B) Evaluated per row
