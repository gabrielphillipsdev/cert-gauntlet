# SC-900 flashcards
# Export for second-model review: FRONT / BACK / explanation. Flag any back or explanation that is factually wrong for the current product, citing Microsoft Learn.

[1] cat=concepts obj=1.1.1 (Describe the shared responsibility model)
FRONT: Shared responsibility — what the customer ALWAYS owns
BACK: #Data, endpoints, accounts and access management | Stays with you in SaaS, PaaS, IaaS and on-premises alike
WHY: Whatever the service model, four things never move to the provider: the information you store, the devices that connect, the user and admin accounts, and the decisions about who may access what. SC-900 stems that say 'regardless of the cloud model' are pointing at this group. Everything else (host, network, OS, runtime, application) slides toward Microsoft as you move from IaaS to PaaS to SaaS.
HOOK: Your data, your devices, your identities: never the cloud provider's problem.

[2] cat=concepts obj=1.1.1 (Describe the shared responsibility model)
FRONT: Shared responsibility — IaaS vs PaaS vs SaaS split
BACK: #IaaS: you run the OS and up | PaaS: provider owns OS and runtime; you own app and data | SaaS: provider runs the application too
WHY: The dividing line moves one layer at a time. With a virtual machine (IaaS) the physical datacenter, network and hosts belong to Microsoft but patching the guest operating system is your job. With a managed platform (PaaS) Microsoft also takes the OS and runtime; you still write and secure the application code. With SaaS such as Microsoft 365 the application is Microsoft's too, leaving you data, identities, devices and configuration choices. The exam loves 'who patches the operating system in a PaaS database' style questions.
HOOK: Count layers: each step toward SaaS hands one more layer to Microsoft.

[3] cat=concepts obj=1.1.2 (Describe defense-in-depth)
FRONT: Defense in depth — the layers from outside in
BACK: #Physical, identity and access, perimeter, network, compute, application, data | Data sits at the center; each layer slows an attacker
WHY: Defense in depth assumes any single control can fail, so controls are stacked so an attacker must beat several in sequence. Microsoft's ordering runs from physical security at the edge through identity and access, perimeter (DDoS protection, firewalls), network (segmentation, NSGs), compute (patched VMs, closed ports), application (secure code) and finally data (encryption, classification). Expect a question that names a control and asks which layer it protects: an NSG is network, Azure DDoS Protection is perimeter, MFA is identity and access.
HOOK: Onion, not wall: peel seven layers to reach the data.

[4] cat=concepts obj=1.1.2 (Describe defense-in-depth)
FRONT: CIA triad — the three goals every layer protects
BACK: #Confidentiality, integrity, availability | Only authorized readers; unaltered data; reachable when needed
WHY: Defense in depth exists to preserve three properties. Confidentiality means only authorized people see the data (encryption, access control). Integrity means data is accurate and only changed through approved processes (hashing, signatures, change control). Availability means authorized users can reach systems when needed (redundancy, DDoS protection, backups). The exam maps scenarios to a letter: a leak is C, tampering is I, an outage or ransomware lockout is A.

[5] cat=concepts obj=1.1.3 (Describe the Zero Trust model)
FRONT: Zero Trust — the three guiding principles
BACK: #Verify explicitly, use least privilege access, assume breach | Authenticate on every signal; grant minimum access; design as if already compromised
WHY: Zero Trust replaces 'trusted inside, untrusted outside' with three rules. Verify explicitly: every request is authenticated and authorized using all available signals such as identity, device health, location and risk. Assume breach: segment, encrypt end to end, monitor and automate response because an attacker may already be inside. A stem describing MFA on every request plus device compliance checks is 'verify explicitly'; limiting blast radius via segmentation is 'assume breach'.
HOOK: Never trust, always verify: three principles, not a product.

[6] cat=concepts obj=1.1.3 (Describe the Zero Trust model)
FRONT: Zero Trust — the foundational pillars
BACK: #Identities, devices, applications, data, infrastructure, networks | Plus visibility, automation and orchestration tying them together
WHY: Microsoft's Zero Trust guidance applies the three principles across pillars: identities verified with strong authentication, devices checked for health and compliance, applications discovered and controlled (including shadow IT), data classified and encrypted, infrastructure continuously assessed, and networks segmented. Microsoft Learn now lists visibility, automation and orchestration as a seventh integrating layer delivered by SIEM and SOAR tooling.

[7] cat=concepts obj=1.1.4 (Describe encryption and hashing)
FRONT: Symmetric vs asymmetric encryption
BACK: #Symmetric: one shared key both ways | Asymmetric: public key encrypts, private key decrypts (and signs)
WHY: Symmetric encryption uses the same secret for encrypting and decrypting, so it is fast and suits bulk data, but the key must be distributed securely. Asymmetric encryption uses a mathematically linked pair: anyone can encrypt with the public key, only the private-key holder can decrypt, and signing with the private key proves authenticity. Real systems combine them: TLS uses asymmetric keys to agree on a symmetric session key. SC-900 asks which type 'uses a public and private key' or 'is used for digital signatures'.

[8] cat=concepts obj=1.1.4 (Describe encryption and hashing)
FRONT: Encryption at rest vs in transit vs in use
BACK: #At rest: stored data on disk or in a database | In transit: data moving over a network (TLS, VPN) | In use: data in memory, protected by confidential computing
WHY: Encryption is described by the state of the data it protects. At rest covers storage: disks, databases, blobs, so a stolen drive is unreadable. In transit covers movement across networks, typically with TLS for HTTPS or IPsec for VPN, defeating eavesdropping. In use is the newest category: data being processed in memory, protected by confidential computing enclaves so even the host OS or hypervisor cannot read it. A stem about 'protecting data traveling between the browser and the web app' is in transit.

[9] cat=concepts obj=1.1.4 (Describe encryption and hashing)
FRONT: Hashing and salting — why they are not encryption
BACK: #Hash: one-way, fixed-length fingerprint, no key | Salt: random value added per password so identical passwords hash differently
WHY: A hash function turns any input into a fixed-length digest that cannot be reversed, which is why systems store password hashes rather than passwords and why a hash can prove a file has not changed. Because the same input always yields the same digest, attackers precompute tables of common passwords; adding a unique random salt before hashing makes those tables useless. Exam signal: 'cannot be decrypted', 'verifies integrity' or 'fixed length' means hashing, and 'random data added to a password' means salting.
HOOK: Encryption is a locked box; a hash is a fingerprint you cannot un-take.

[10] cat=concepts obj=1.1.5 (Describe Governance, Risk, and Compliance (GRC) concepts)
FRONT: Governance, risk and compliance — the three defined
BACK: #Governance: rules and processes that direct the organization | Risk: identify, assess, respond to and monitor threats | Compliance: meeting the laws, standards and policies that apply
WHY: GRC is the management side of security. Governance sets policy, ownership and accountability, for example rules about classifying and retaining data or approving privileged access. Risk management is a loop of identifying threats, assessing impact and likelihood, responding (accept, mitigate, transfer, avoid) and monitoring. Compliance is adherence to the laws and standards that apply to your industry, region and data. Compliance Manager and Purview are the Microsoft tools that operationalize this.
HOOK: Governance decides, risk weighs, compliance proves.

[11] cat=concepts obj=1.1.5 (Describe Governance, Risk, and Compliance (GRC) concepts)
FRONT: Data residency vs data sovereignty vs data privacy
BACK: #Residency: rules on where data may be stored and transferred | Sovereignty: data is subject to the laws of where it physically sits | Privacy: appropriate handling of personal data
WHY: Three terms the exam likes to swap. Data residency is about geography: regulations that fix the physical locations where data can be stored and when it can cross borders. Data sovereignty is about jurisdiction: data collected or held in a country is governed by that country's laws, whatever the owner's nationality. A stem about choosing an Azure region to satisfy a national law is residency; one about GDPR rights of individuals is privacy.

[12] cat=concepts obj=1.2.1 (Define identity as the primary security perimeter)
FRONT: Identity as the primary security perimeter
BACK: #The network edge no longer bounds the enterprise | Every access decision starts with who or what is asking
WHY: With SaaS apps, mobile devices and remote work, resources live outside any firewall, so a corporate network boundary cannot be the control point. Instead each access request is evaluated on the identity presenting it: a person, a service, or a device. This is why Microsoft treats Entra ID as the control plane and why Zero Trust begins with verifying identity. On SC-900, 'identity is the new security perimeter' is a phrase to recognize and to connect with Conditional Access and MFA.

[13] cat=concepts obj=1.2.1 (Define identity as the primary security perimeter)
FRONT: Four pillars of an identity infrastructure
BACK: #Administration, authentication, authorization, auditing | Create and govern identities; prove them; grant rights; record what happened
WHY: Microsoft Learn frames identity management as four pillars. Administration is the lifecycle of identities and their governance. Authentication is proving the identity is who it claims to be. Authorization decides what an authenticated identity may do. Auditing tracks who did what, when and how, so that access can be reviewed and anomalies spotted. An exam stem that mentions 'tracking and reviewing access activity' is auditing; one about creating and removing accounts is administration.

[14] cat=concepts obj=1.2.2 (Define authentication)
FRONT: Authentication — defined
BACK: #Proving an identity is who it claims to be | Password, MFA, certificate, biometric; often shortened to AuthN
WHY: Authentication is the act of confirming an identity before any access decision is made. The user, device or workload presents credentials: something known (password), something held (phone, FIDO2 key, certificate) or something inherent (fingerprint, face). Only once the claim is verified does the system move on to decide what that identity may do. SC-900 contrasts it with authorization and expects you to know that MFA strengthens authentication, not authorization.
HOOK: AuthN answers 'who are you?' before anyone asks 'what may you do?'

[15] cat=concepts obj=1.2.2 (Define authentication)
FRONT: Multifactor authentication — the factor categories
BACK: #Something you know, something you have, something you are | Two or more different categories, not two of the same
WHY: MFA requires evidence from at least two distinct categories: knowledge such as a password or PIN, possession such as a phone running an authenticator app or a hardware key, and inherence such as a fingerprint or face. Two passwords are still one factor. The practical point on SC-900 is that a stolen password alone is not enough when a second category is enforced, which is why Microsoft treats MFA as the single most effective control against account compromise.

[16] cat=concepts obj=1.2.3 (Define authorization)
FRONT: Authorization — defined
BACK: #Deciding what an authenticated identity can do | Roles, permissions and policies; often shortened to AuthZ
WHY: Authorization comes after authentication and determines the level of access: which resources, which operations, under what conditions. In Microsoft's world this is expressed through role assignments (Entra roles, Azure RBAC), app permissions, sharing settings and policies. The stem signal is 'determine the level of access' or 'grant permission to'. If a question says a user signed in successfully but cannot open a file, the failure is authorization, not authentication.

[17] cat=concepts obj=1.2.3 (Define authorization)
FRONT: Authentication vs authorization — the one-line contrast
BACK: #AuthN proves identity; AuthZ grants permissions | Sign-in succeeds, then the role decides what you can touch
WHY: The pair is tested as a sentence-completion item. Authentication (AuthN) is the process of verifying that a user, device or service is who it claims to be. Authorization (AuthZ) is the process of granting that verified identity the appropriate level of access to resources. Both are needed and they happen in that order. Microsoft Entra ID performs both: it authenticates sign-ins and issues tokens, and it enforces authorization through roles, Conditional Access and application permissions.
HOOK: N before Z: you cannot be authorized until you are authenticated.

[18] cat=concepts obj=1.2.4 (Describe identity providers)
FRONT: Identity provider (IdP) — the role
BACK: #Creates, maintains and manages identities and authenticates them | Issues security tokens that applications trust
WHY: An identity provider holds the identity data, performs the authentication and then hands the application a signed token describing the user and their claims, so the app never sees the password. Microsoft Entra ID is the identity provider for Microsoft cloud services and for any registered application. Because one IdP can vouch to many apps, it enables single sign-on. Exam signal: 'modern authentication', 'tokens' and 'central identity service' all describe the IdP role.

[19] cat=concepts obj=1.2.4 (Describe identity providers)
FRONT: Single sign-on (SSO) — what the IdP enables
BACK: #Authenticate once, access many apps without re-signing in | The IdP's token is accepted by every connected application
WHY: Because applications trust the identity provider's tokens rather than keeping their own password databases, a user who has authenticated to the IdP can be silently signed in to other connected applications. This improves user experience and security at the same time: fewer passwords to manage, one place to enforce MFA and Conditional Access, and one place to cut off access when someone leaves. SC-900 pairs SSO with the identity provider concept and with federation across organizations.

[20] cat=concepts obj=1.2.5 (Describe the concept of directory services and Active Directory)
FRONT: Directory service and Active Directory Domain Services
BACK: #A directory stores identity data for network objects | AD DS: on-premises directory on domain controllers, Kerberos/NTLM, Group Policy
WHY: A directory service is a hierarchical store of information about users, groups, computers and policies that answers 'who is this' and 'what may they access'. Active Directory Domain Services is Microsoft's on-premises implementation: domain controllers hold the database, authenticate with Kerberos and NTLM, and push configuration through Group Policy and organizational units. Its limitations in the exam framing are that it has no native support for cloud and SaaS apps, mobile platforms, or modern protocols such as OAuth 2.0 and OpenID Connect.

[21] cat=concepts obj=1.2.5 (Describe the concept of directory services and Active Directory)
FRONT: AD DS vs Microsoft Entra ID — the contrast
BACK: #AD DS: on-premises, Kerberos/NTLM, Group Policy, VPN for remote | Entra ID: cloud IDaaS, OAuth 2.0/OIDC/SAML, SaaS and any device
WHY: The exam positions Entra ID as the evolution of directory services for the internet era rather than a cloud copy of AD DS. AD DS manages domain-joined Windows machines inside a network boundary using Kerberos, NTLM and Group Policy. Entra ID is identity as a service: it authenticates to cloud and SaaS applications with modern protocols, supports any platform, and needs no VPN. Hybrid identity connects the two so one set of credentials works for both. A stem about 'Kerberos' or 'Group Policy' means AD DS; 'OAuth' or 'SaaS apps' means Entra ID.

[22] cat=concepts obj=1.2.6 (Describe the concept of federation)
FRONT: Federation — defined
BACK: #A trust relationship between an identity provider and a service provider | Users of one domain access another's resources with their home credentials
WHY: Federation lets an organization accept identities authenticated elsewhere. The service provider is configured to trust tokens issued by a partner identity provider, so a user signs in at home and presents the resulting token to the other side without ever creating a second password. This is the mechanism behind cross-organization collaboration and behind connecting on-premises AD FS to Entra ID. Exam signal: 'users from a partner organization sign in with their own credentials' or 'trust relationship between two IdPs'.

[23] cat=concepts obj=1.2.6 (Describe the concept of federation)
FRONT: Federation trust — direction
BACK: #Trust is not automatically mutual | A accepting B's tokens does not mean B accepts A's
WHY: A federated trust is established from the relying party toward the identity provider it chooses to believe. If Woodgrove's app trusts Fabrikam's identity provider, Fabrikam users can reach Woodgrove resources, but nothing yet lets Woodgrove users into Fabrikam. Bidirectional access requires configuring the trust in both directions. The exam tests this with a true/false style statement about whether federation is 'always bidirectional'; it is not.
HOOK: Trust points one way until you draw the second arrow.

[24] cat=entra obj=2.1.1 (Describe Microsoft Entra ID)
FRONT: Microsoft Entra ID — what it is
BACK: #Microsoft's cloud-based identity and access management service | Authenticates users, devices and workloads; enforces Conditional Access; issues tokens
WHY: Microsoft Entra ID (formerly Azure Active Directory) is the identity provider for Microsoft 365, Azure, Dynamics and any application you register with it. Every Microsoft 365 or Azure subscription already has a tenant. It handles authentication with modern protocols, authorization through roles and app permissions, policy enforcement through Conditional Access, and risk detection through ID Protection. On SC-900 it is the answer whenever a stem asks which service 'manages identities and access for cloud resources'.

[25] cat=entra obj=2.1.1 (Describe Microsoft Entra ID)
FRONT: Entra ID editions
BACK: #Free, P1, P2, plus ID Governance and other Entra products | P1 adds Conditional Access; P2 adds ID Protection and PIM
WHY: Licensing questions on SC-900 stay at the edition level. Free comes with any Microsoft cloud subscription and covers core directory, SSO and basic security defaults. P1 unlocks Conditional Access, hybrid features such as password writeback, and dynamic groups. P2 adds Identity Protection risk policies and Privileged Identity Management. Stem signal: 'which minimum edition is required for risk-based Conditional Access' is P2.
HOOK: P1 = Conditional Access, P2 = risk and PIM, Governance = lifecycle.

[26] cat=entra obj=2.1.2 (Describe types of identities, including workload identities)
FRONT: Entra identity types — the four kinds
BACK: #Users, groups, devices, workload identities | Human and non-human identities all get an object in the directory
WHY: Everything that needs to authenticate or be granted access has an identity object in Entra ID. Users are people, internal or external. Groups bundle users for assignment; security groups control access while Microsoft 365 groups also provide collaboration resources. Devices are registered or joined endpoints that can be targeted by Conditional Access. Workload identities are applications, service principals and managed identities, the software equivalents of a user. The exam asks you to classify a scenario into one of these buckets.

[27] cat=entra obj=2.1.2 (Describe types of identities, including workload identities)
FRONT: Service principal vs application object
BACK: #Application object: the global template, in the home tenant | Service principal: the local instance in each tenant that uses the app
WHY: When an app is registered, Entra ID creates an application object in the home tenant describing how tokens are issued and what the app needs. Every tenant where the app is actually used gets a service principal, the identity the app signs in as and the object you assign roles and permissions to. One application object can therefore have many service principals across tenants. Exam signal: 'the identity an application uses to access resources in your tenant' is the service principal.

[28] cat=entra obj=2.1.2 (Describe types of identities, including workload identities)
FRONT: Managed identity — system-assigned vs user-assigned
BACK: #A service principal whose credentials Azure manages for you | System-assigned: tied to one resource's lifecycle | User-assigned: standalone, shared by several resources
WHY: Managed identities remove secrets from code: an Azure resource such as a VM, function or Logic App gets an identity in Entra ID and Azure rotates its credentials automatically. A system-assigned identity is created with the resource and deleted with it. A user-assigned identity is its own Azure resource that can be attached to multiple workloads and outlives any one of them. Stem signal: 'an Azure VM must read secrets from Key Vault without storing credentials' points to a managed identity.
HOOK: System-assigned dies with the resource; user-assigned lives on its own.

[29] cat=entra obj=2.1.2 (Describe types of identities, including workload identities)
FRONT: External identities — B2B collaboration guest
BACK: #Partner users invited into your tenant as guest objects | They sign in with their own home credentials
WHY: Microsoft Entra B2B collaboration lets you invite people from other organizations; a guest user object is created in your workforce tenant and can be added to groups and assigned access like an employee, but authentication still happens at their home identity provider or via a one-time passcode. B2B direct connect is different: it creates a two-way trust for Teams shared channels without adding guest objects. External ID for customers is the separate CIAM product for consumer-facing apps. SC-900 mainly tests the guest-user model.

[30] cat=entra obj=2.1.2 (Describe types of identities, including workload identities)
FRONT: Device identities — registered, joined, hybrid joined
BACK: #Registered: personal/BYOD devices, cloud SSO only | Joined: organization-owned Windows, Entra account sign-in | Hybrid joined: on-premises domain joined AND registered with Entra
WHY: A device identity lets Conditional Access require a compliant or managed device. Entra registered suits bring-your-own devices and phones that need access to work resources. Entra joined is for organization-owned Windows devices that sign in with an Entra account and get SSO to cloud and on-premises resources. Entra hybrid joined covers machines already joined to on-premises AD DS that are also registered in the cloud, typically as a transition state. Exam signal: 'personal device' is registered; 'already domain-joined' is hybrid joined.

[31] cat=entra obj=2.1.3 (Describe hybrid identity)
FRONT: Hybrid identity — the concept
BACK: #One identity usable on-premises and in the cloud | AD DS objects synchronized to Entra ID with Entra Connect or Cloud Sync
WHY: Most organizations still run AD DS, so hybrid identity synchronizes users, groups and password hashes into Entra ID. Users then sign in to Microsoft 365 with the same credentials they use at the office. Two tools do the synchronization: Microsoft Entra Connect Sync, the full on-premises sync engine, and Microsoft Entra Cloud Sync, a lightweight agent orchestrated from the cloud. The sign-in method chosen (PHS, PTA or federation) decides where the password is checked.

[32] cat=entra obj=2.1.3 (Describe hybrid identity)
FRONT: Entra Connect sign-in methods — PHS vs PTA vs federation
BACK: #PHS: hash of the hash synced; cloud validates | PTA: agent validates against on-premises AD in real time | Federation: AD FS or third-party IdP issues the token
WHY: Password hash synchronization copies a hashed form of each user's password hash to Entra ID, so authentication works in the cloud even if the datacenter is down; Microsoft recommends it as the simplest option. Pass-through authentication keeps passwords on-premises: a lightweight agent validates each sign-in against AD DS live, so on-premises policies apply immediately. Stem signal: 'passwords must never leave the on-premises network' excludes PHS.
HOOK: PHS: cloud checks; PTA: agent checks; federation: someone else checks.

[33] cat=entra obj=2.1.3 (Describe hybrid identity)
FRONT: Microsoft Entra Cloud Sync — how it differs from Connect Sync
BACK: #Lightweight provisioning agent, configuration lives in the cloud | Handles multiple disconnected AD forests; outbound-only connections
WHY: Cloud Sync moves the sync logic into Microsoft Online Services and leaves only a small provisioning agent on-premises that needs outbound connectivity and updates itself. It can synchronize several disconnected forests to one tenant, which the classic Connect Sync server struggles with, and Microsoft positions it as the future direction. Connect Sync remains the choice when you need features Cloud Sync lacks, such as device object sync or pass-through authentication.

[34] cat=entra obj=2.2.1 (Describe the authentication methods)
FRONT: Passwordless methods in Entra ID
BACK: #Windows Hello for Business, FIDO2 security keys/passkeys, Authenticator app sign-in | Certificate-based authentication also counts as phishing-resistant
WHY: Passwordless sign-in replaces the password with a possession factor unlocked by a biometric or PIN. Windows Hello for Business ties the credential to the device TPM. FIDO2 security keys and passkeys (including passkeys stored in Microsoft Authenticator) use public-key cryptography bound to the site, which is why Microsoft classes them as phishing-resistant. Certificate-based authentication with smart cards is phishing-resistant too. Exam signal: 'highest security' or 'phishing-resistant' points to FIDO2, Hello or CBA.

[35] cat=entra obj=2.2.1 (Describe the authentication methods)
FRONT: Microsoft Authenticator app — what it provides
BACK: #Push notification approval, time-based codes, passwordless phone sign-in | Can also hold a passkey for phishing-resistant sign-in
WHY: The Authenticator app is the most common MFA method in Entra ID. As a second factor it can send a push notification the user approves (with number matching) or generate a six-digit time-based code that works offline. Configured for phone sign-in it becomes a primary passwordless method. Newer versions can store a passkey, elevating it to phishing-resistant. For SSPR it supplies either a notification or a code. When a stem asks for an MFA method that 'works without cellular signal', the app's code is the answer rather than SMS.

[36] cat=entra obj=2.2.1 (Describe the authentication methods)
FRONT: OATH tokens, SMS and voice — the weaker methods
BACK: #OATH software/hardware tokens: time-based codes | SMS and voice call: codes or call-back via the phone network, MFA and SSPR only
WHY: OATH TOTP tokens generate a rotating code from a shared seed; software tokens run in an authenticator app, hardware tokens are key-fob devices (Microsoft Learn still lists hardware OATH tokens as preview). SMS and voice call deliver a code or a call the user answers; they are easy to deploy but exposed to SIM swapping and interception, so Microsoft rates them medium security and recommends moving away from them. SMS can also be a primary sign-in method for frontline workers. Exam signal: 'least secure' among MFA options is SMS or voice.

[37] cat=entra obj=2.2.1 (Describe the authentication methods)
FRONT: Temporary Access Pass (TAP)
BACK: #Time-limited, admin-issued passcode used once or for a window | Bootstraps passwordless registration or recovers a lost device
WHY: A Temporary Access Pass is a code an administrator creates for a specific user with a lifetime and optional single-use setting. The user signs in with it to register strong methods such as a FIDO2 key or the Authenticator app, which solves the chicken-and-egg problem of passwordless onboarding. It also serves as recovery when someone loses their phone. Lifecycle workflows can issue one automatically on a new hire's first day. Stem signal: 'new employee must set up passwordless on day one' or 'temporarily' plus 'strong authentication' means TAP.
HOOK: TAP is the one-time key that lets you enroll the real keys.

[38] cat=entra obj=2.2.1 (Describe the authentication methods)
FRONT: Windows Hello for Business vs FIDO2 security key
BACK: #Hello: credential bound to one device, unlocked by PIN or biometric | FIDO2 key: portable hardware credential usable on any supported device
WHY: Both are phishing-resistant passwordless methods built on asymmetric keys. Windows Hello for Business creates the key pair inside a specific PC's hardware and gates it behind a PIN, face or fingerprint; it is tied to that device. A FIDO2 security key is a USB, NFC or Bluetooth device the user carries from machine to machine, which suits shared workstations and kiosks. The exam contrasts them on portability: 'users move between shared devices' favors FIDO2, 'sign in to their own laptop with a fingerprint' is Hello.

[39] cat=entra obj=2.2.2 (Describe multifactor authentication (MFA))
FRONT: Multifactor authentication in Entra ID — ways to require it
BACK: #Security defaults (tenant-wide, free), Conditional Access (granular, P1) | Legacy per-user MFA is the older model Microsoft is retiring
WHY: Entra MFA prompts for a second verification after the password. The quickest way to turn it on for everyone is security defaults, a free preconfigured setting that also blocks legacy authentication. Conditional Access policies give granular control: require MFA only for admins, only outside trusted locations, only for risky sign-ins. On SC-900 'enable MFA for all users with no additional licensing' is security defaults; 'require MFA only when the sign-in comes from an unfamiliar location' is Conditional Access.

[40] cat=entra obj=2.2.2 (Describe multifactor authentication (MFA))
FRONT: Why MFA matters — the exam framing
BACK: #A compromised password alone no longer grants access | Second factor comes from a different category than the first
WHY: Microsoft's guidance repeatedly states that enabling MFA is the single most effective step against identity attacks because the vast majority of account compromises use only a stolen or guessed password. The second factor must come from another category (possession or inherence), so a phished password is useless without the user's phone or key. SC-900 may phrase this as a true/false statement: MFA is 'something you know plus something you have or are', and it is enforced during authentication rather than authorization.

[41] cat=entra obj=2.2.3 (Describe password protection and management capabilities)
FRONT: Self-service password reset (SSPR)
BACK: #Users reset, change or unlock their own account without help desk | Admin sets 1 or 2 required methods; writeback syncs the change to AD DS
WHY: SSPR lets a user who forgot a password or locked an account recover it by proving identity with registered methods: Authenticator notification or code, email, SMS, voice or OATH token. Administrators choose whether one or two methods are required; admin accounts with Entra roles always need two. For hybrid users, password writeback pushes the new password back to on-premises AD DS, which requires Entra ID P1. Exam signal: 'reduce help-desk calls for forgotten passwords' is SSPR; 'the reset must update the on-premises password' needs writeback.

[42] cat=entra obj=2.2.3 (Describe password protection and management capabilities)
FRONT: Entra Password Protection — banned password lists
BACK: #Global banned list from Microsoft telemetry, always on | Custom banned list of up to 1,000 org-specific terms; extends to on-premises AD DS
WHY: Password Protection blocks weak passwords at change or reset time. The global banned password list is built by Microsoft from observed attacks and cannot be disabled or viewed. The custom list adds up to 1,000 organization-specific base terms such as brand names, locations or product names; the matching algorithm handles substitutions like 0 for o and fuzzy variants automatically. Stem signal: 'prevent users from choosing passwords that contain the company name' is the custom banned list.
HOOK: Ban the root word; the algorithm catches C0ntos0!.

[43] cat=entra obj=2.2.3 (Describe password protection and management capabilities)
FRONT: Smart lockout
BACK: #Locks out attackers guessing passwords while sparing real users | Default: 10 failed attempts, 60-second lockout that grows; separate counters for familiar locations

[79] cat=aznet obj=3.1.5 (Describe network security groups (NSGs))

[145] cat=purview obj=4.3.6 (Describe retention policies, retention labels, and retention label policies)

BACK: #1 Retention wins over deletion · 2 Longest retention period wins | 3 Explicit (label) wins over implicit (policy) | 4 Shortest deletion period wins
WHY: When several retention settings apply to one item, Purview applies four rules in order. First, if anything says retain, the item is kept, even if another setting says delete.
