# SC-200 pack — content spec (plus AZ-900 / SC-900 warm-up decks)

Written by Chat 5 from PLAN.md §4 and the sec-study schema (CARDS_SPEC / PRACTICE_SPEC / EXAM_SPEC), then reconciled with Chat 1's `dev/ENGINE.md`. Every content file is an ES module that `export const`s one array; `packs/<id>/pack.js` is the manifest whose `load()` imports them (see ENGINE.md → Pack manifest). Manifests declare `objPattern` because Microsoft objective ids are three-level (`1.4.3`), and `validator: dev/check-sc200.js` for the Microsoft item types the generic `dev/check-pack.mjs` doesn't know. Fidelity checklist: `dev/FIDELITY-sc200.md`.

## 3. Card schema (same as sec-study, plus `obj`)

```js
{c:"ingest", obj:"1.3.2",
 q:"Data collection rule (DCR) — what it does",                 // FRONT ≤ 90 chars
 a:"#Defines what AMA collects and where it lands\nXPath filters for events; destination workspace/table",  // BACK, \n lines, # line = headline, ≤ 3 lines
 s:"Tells the AMA agent what to collect and which workspace gets it",   // OPTIONAL MC short ≤ 60 chars; unique within category; reads as an option
 x:"2–4 sentences, 200–560 chars. What it is, why it matters on SC-200, how it differs from its neighbor (DCR vs connector), and the stem wording that signals it.",
 w:"Optional hook ≤ 120 chars (~25% of cards)",
 g:"optional distractor group key",
 k:"optional KQL snippet shown in monospace on the BACK (\\n for lines)"}  // use on KQL cards
```
Rules carried over: original text; atomic; distinct shorts per category; exam-keyword aware; no HTML; escape `"`. New: `k` holds query text for KQL cards; `q` may ask "which table…" / "which operator…".

## 4. Twins (same as sec-study, plus `obj`)

## 5. Portal-navigation / hot-area deck

```js
{id:"p001",obj:"1.1.3",portal:"defender",            // defender | azure | purview | entra | intune
 q:"Where do you turn on Live Response for the tenant?",
 path:["Settings","Endpoints","Advanced features"],  // the click path, top-level first; the LAST entry is the hot-area target page
 target:"The 'Live Response' toggle in the Advanced features list",   // what the user must click on the final screen
 regions:[{l:"Advanced features",ok:true},{l:"Rules",ok:false},{l:"Permissions",ok:false},{l:"Device management",ok:false}],  // 4–6 labelled regions, exactly one ok — these become hot-area rectangles once a screenshot is attached
 img:null,                                            // screenshot path later (Chat 6); null for now
 x:"Why it lives here + the neighbors people confuse (2–3 sentences)."}
```
Regions must be real UI labels that appear together on the final screen so a screenshot can be hot-area'd with no text changes. Cover all 3 domains roughly 35/15/10 and all portals.

## 6. Exam banks — Microsoft item types

Each bank is an array of **50 question units**: 38 standalone items + 1 case study (8 questions) + 1 solution series (4 yes/no). Validator counts units, not objects. Domain quota per bank (units): d1 **21**, d2 **19**, d3 **10** (case-study and series questions count toward quota with their own `d`).

Common fields on every object: `id` (bank letter + 3 digits, sequential in file order; case/series are one object each), `d`, `obj`, `cat`, `t`, `w` (takeaway ≤ 260). Stems ≤ 500 chars, options ≤ 120, option `x` ≤ 280. Addresses from RFC 5737/1918; no real company names; fictional tenant "Contoso-style" names are fine (use *Fabrikam*, *Northwind*, *Tailspin*, *Woodgrove*, *Litware* — Microsoft's own fictional set).

### 6.1 `mc` — single answer (exactly 4 options, 1 ok)
```js
{id:"a001",d:1,obj:"1.4.3",cat:"detect",t:"mc",
 q:"…Which rule type should you use?",
 ex:"optional monospace exhibit (KQL, alert JSON, table rows, DCR snippet) ≤ 14 lines",
 o:[{t:"NRT rule",ok:true,x:"why"},{t:"…",ok:false,x:"why not here"},…],
 w:"takeaway"}
```
### 6.2 `ms` — multi-response (`pick` 2–3, 5–6 options, exactly `pick` ok). Microsoft phrasing: "Which two actions should you perform? Each correct answer presents part of the solution." or "…presents a complete solution." Say which in the stem.

### 6.3 `order` — drag-drop ordering (all pool items used)
```js
{id:"a007",d:2,obj:"2.2.2",cat:"dferesp",t:"order",
 q:"You need to collect volatile evidence from a device and then isolate it. Which four actions should you perform in sequence?",
 pool:["Initiate a live response session","Run getfile to retrieve the suspicious binary","Collect an investigation package","Isolate the device"],  // 4–6, shown shuffled
 answer:[0,1,2,3],                       // indices into pool, correct order
 alt:[[0,2,1,3]],                        // OPTIONAL additional accepted orders (equivalent sequences)
 x:"Why this order (2–4 sentences).",w:"…"}
```
### 6.4 `build` — build list (choose the right subset, then order it)
Same shape as `order`, but `pool` has 6–8 entries including distractors and `answer` lists only the needed ones (3–5). `ordered:true|false` — Microsoft build lists are usually ordered; set `false` when sequence doesn't matter (graded as a set).

### 6.5 `hot` — hot area (text-described until screenshots land)
```js
{id:"a012",d:1,obj:"1.1.6",cat:"dfecfg",t:"hot",
 q:"On the ASR rule configuration shown, which setting blocks Office apps from creating child processes without affecting the other rules?",
 screen:"Describe the screen in words: a settings list with these rows…",
 regions:[{l:"Block all Office applications from creating child processes — Block",ok:true},{l:"…",ok:false},…],  // 4–8, pick = number ok
 pick:1,img:null,x:"…",w:"…"}
```
Optional in banks (0–2 per bank); required type for the portal deck.

### 6.6 `case` — case study (one per bank, exactly 8 questions)
```js
{id:"a039",t:"case",title:"Fabrikam SOC consolidation",
 tabs:{overview:"…",environment:"…",requirements:"…",issues:"…"},   // each ≥ 300 chars; 'issues' = existing problems the questions hinge on
 questions:[ {id:"a039-1",d:1,obj:"1.3.2",cat:"ingest",t:"mc",q:"…",o:[…],w:"…"}, … 8 of mc/ms/order/build, each referencing the tabs ]}
```
Questions must be unanswerable without the tabs (reference a requirement or issue by content). Mix ≥2 domains.

### 6.7 `series` — problem-solution yes/no series (one per bank, exactly 4)
```js
{id:"a040",d:1,obj:"1.1.10",cat:"sentauto",t:"series",
 scenario:"Shared scenario + goal statement ending in 'Does the solution meet the goal?' style (≥ 200 chars).",
 solutions:[{s:"Solution: You create an automation rule that…",ok:false,x:"why not"},{…},{…},{…}]}  // exactly 4; 1 or 2 ok (never 0, never 4)
```
Validator checks each series has 1–2 `ok:true` and that all four `s` differ.

### 6.8 Bank mix (standalone 38): ≥ 6 `ms`, ≥ 3 `order`, ≥ 3 `build`, 0–2 `hot`, rest `mc`; ≥ 8 with `ex` exhibits (KQL query + result rows, incident JSON, DCR XPath, Logic App step list, device timeline rows, EmailEvents rows, Purview audit record, alert tuning rule). File order: case study **first** (Microsoft opens with it), series **last**, standalone shuffled across domains between them.

## 7. Fundamentals decks (AZ-900, SC-900)

Cards: schema §3 with `c` from the fundamentals skills JSON and `obj` from it. Questions: bank schema `mc`/`ms` only (ids `z001…z050` AZ-900, `s001…s050` SC-900), quota per `questionQuota` in the JSON, ≥ 6 `ms` each. Fundamentals voice: "Which Azure service…", "Select the answer that correctly completes the sentence", true/false-style statements rendered as `ms` with `pick` = number of true statements.

## 8. Validators & exports

`node dev/check-sc200.js all` runs everything and prints PASS/FAIL with counts vs targets. It enforces: schema per type, `obj` ids exist, category→domain consistency, per-category minimums and targets (±10%), unique `q` per category, unique shorts per category, unique stems per bank (and across banks), domain quotas, format mix, case/series shapes, order/build index validity, hot-area single-ok, portal regions ≥ 4 with one ok, no HTML, length limits (warn). `node dev/export-sc200.js` writes `dev/export/sc200-bank-a.txt` … with answers marked so a second model can hunt for wrong keys.

## 10. Product drift noted while authoring (Oct 2, 2026) — keep in sync with the exam outline

These are current Microsoft Learn statements that differ from older study material. Items in this pack follow the current docs; the Oct 21, 2026 outline still lists the older feature names, so cards explain both.

- **AIR on Defender for Endpoint**: as of Sept 1, 2026 AIR no longer runs as a separate investigation or can be triggered manually on devices (DfO365 AIR remains). Device-group automation levels still exist and govern attack-disruption/response approvals; pending actions still expire after 7 days.
- **Sentinel livestream** is retired (Hunting shows Hunts / Queries / Bookmarks). Used only as a distractor.
- **NRT rules** now support multiple tables and cross-workspace queries (50 per workspace, 1-min cadence, 2-min delay). Single-table/no-join limits apply to **Defender XDR custom detections in Continuous (NRT)** frequency.
- **Custom detection columns**: Timestamp/ReportId and an impacted-entity column are *recommended* (the service evaluates ingestion_time() itself).
- **ThreatIntelligenceIndicator** stopped receiving data July 2025 → `ThreatIntelIndicators` / `ThreatIntelObjects`.
- **Classic Content search** retired Aug 2025 → searches live inside the unified eDiscovery experience.
- **MailItemsAccessed** is part of Audit (Standard); Standard retention 180 days, Premium 1 year (10-year add-on).
- **Alert tuning** actions: Hide, Resolve, Set as behavior. Unified RBAC default for new DfE tenants since Feb 2025.
- **Live response** limits: 50 concurrent sessions per tenant, 5 per user, 30-min idle timeout.
- **Defender for Cloud Apps file policies** retire Jan 6, 2027. Sentinel in the Azure portal ends after Mar 31, 2027.
- **Review pass**: an independent agent reviewed every bank item, every twin and portal item, and all number/name-bearing cards against Learn; 1 wrong key (fixed), 5 fact errors (fixed), 7 ambiguities (fixed). Second-model review via `dev/export/*.txt` is still the next gate.
